## 계획 대비 실제
- 계획대로 된 것: S1 `scripts/install-app.sh`(사전 점검 → 빌드 → `build-commit` 기록 → 종료·`ditto` 교체 → 실행)와 S2 앱 메뉴 연결. `check-install-app.sh` 3/3 통과. 실제 설치 뒤 `build-commit` = main HEAD `0c39c2c`를 확인했다.
- 어긋난 것 — **실제 대상에 처음 돌릴 때 점검이 못 잡은 문제 셋**:
  - **첫 설치 필요**: `/Applications/Anvil.app`이 아예 없었다. 사용자가 띄워 둔 앱은 기능 추가 전의 디버그 빌드(`target/debug/bundle`)라 메뉴 항목도 없었다. 자체 업데이트 기능은 처음 한 번은 손으로 설치해야 쓸 수 있다.
  - **`.claude/` 미추적 폴더**: 기본 체크아웃 아래 Claude 워크트리가 `?? .claude/`로 잡혀 '변경 없음' 점검에서 막혔다 → `.gitignore`에 추가했다(#16).
  - **로컬 main 추적 브랜치 없음**: 인자 없는 `git pull --ff-only`가 실패했다 → `git pull --ff-only origin main`으로 명시했다(#17).
  - fg-loop의 C3(`evidence: external`)는 "사람이 메뉴로 업데이트하면 된다"고 가정했다. 그래서 두 번 연속 변화 없이 대기하다 '대기 정체' 벽에서 멈췄고, 위 문제들은 그 뒤에 사람과 함께 하나씩 풀었다.

## 배운 점
- 다음엔 다르게:
  - **설치·배포 스크립트는 점검용 임시 레포만으로 끝내지 말고, 실제 체크아웃 상태(미추적 폴더·upstream 유무·설치 대상 존재)를 읽기 전용으로 먼저 확인한다.** 실패 3종 단언은 통과했지만 실제 환경 셋 모두에서 막혔다.
  - **git pull은 리모트·브랜치를 명시한다.** 체크아웃마다 upstream 설정이 다르다.
  - **외부 증거 점검(`evidence: external`)을 정할 때 "사람이 그 행동을 할 수 있는 상태인가"(설치본 존재, 메뉴가 있는 빌드인가)까지 전제로 적는다.** 대기만 하다 정체 벽에서야 드러났다.
  - 앱의 `REPO_DIR`은 빌드한 체크아웃을 가리킨다. 워크트리에서 빌드한 앱의 메뉴는 그 워크트리를 업데이트하므로, 설치본은 기본 체크아웃에서 빌드한다.
