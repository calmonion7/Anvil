# 실행 기록 — 재부팅·서버 재시작 뒤 세션을 대화째 복구 (데스크톱 앱 2/6)

fg-loop 무인 드라이브가 맡긴 실행이다. 워크플로 없이 이 세션이 직접 실행했다. 조각이 S1 → S2 두 개뿐이고 서로 이어진다. 계획에 `tdd: on`이 있어 테스트(`server/test/restore.test.js`)를 먼저 쓰고 빨강(5/5 실패)을 확인한 뒤 구현했다.

## 조각별 결과
- S1 복구 목록 기록(`restore.json`, 원자적 갱신·600, 세션 시작·훅 대화 ID·[세션 종료]·스스로 종료) — ✅ 계획대로
- S2 서버 시작 때 복구(`ready` 단계 — 포트를 잡은 뒤, 등록 해제 항목 빼기, ID 없으면 새 대화) — ⚠ 독립 검사(C2)가 틈을 잡았다. 훅이 대화 ID를 알린 직후(목록 반영 150ms 지연 안) 서버가 죽으면 `--resume` 없이 떴다. 복구할 때 훅이 직접 쓴 상태 파일의 ID를 먼저 보게 고쳤다. `/clear` 직후도 함께 해결된다.

## 계획 밖 변경
- 세션 복구를 `init`이 아니라 새 모듈 단계 `ready`에서 한다. 코어가 포트·토큰·`server.json`을 쓴 뒤 부른다(`server/http.js`). 포트를 못 잡은 두 번째 서버가 claude를 띄워 첫 서버 세션의 상태 파일을 덮지 않게 하려는 것이다. `server/API.md` 모듈 규약에 적었다.
- 대화 ID 모양 검사(`^[A-Za-z0-9][\w-]*$`)를 넣었다. 상태 파일 값을 claude 인자로 넘기므로 `--…` 꼴이면 옵션으로 읽힐 수 있다. 같은 사용자 권한이 있어야 건드릴 수 있는 파일이라 위험은 낮지만 고치는 비용이 거의 없다. 테스트로 고정했다.
- Electron 스모크(`e2e-app/app.spec.ts`)에 복구 시나리오 테스트를 하나 더했다. 같은 테스트 안에 단계를 끼우지 않고 독립 테스트로 둬서, 1/6 시나리오와 서로 영향을 주지 않는다.

## DoD 기준선 → 실행 뒤
1. `node --test server/`: 82/82 → 88/88(두 번). 새 테스트 6개: 목록 기록·사람이 끝낸 세션 빼기·SIGTERM 복구·SIGKILL 복구·목록 반영 전 사망·ID 없음/등록 해제/옵션 모양 ID.
2. `npx playwright test`: 43 passed → 43 passed. 회귀 방지 검사라 그대로인 것이 정상이다.
3. `npm run test:app`: 1 passed → 2 passed. 새 테스트는 세션 열기 → 앱 끄기 → 서버 SIGKILL → 앱 다시 실행 → 같은 세션 살아 있음, 가짜 claude가 `--resume <ID>`를 받음을 본다.
4. UAT — 아래 STATUS `verified:`.
- 루프 독립 검사 C2 `restore-probe.mjs`: 2 FAIL·3 PASS → 처음 실행에서 2 FAIL(`fake claude got --resume` 시간 초과 — 위 틈) → 고친 뒤 5 PASS.
- `npm run check`: 0 오류 → 0 오류.

## Rulings
- 실행 방식: 워크플로 대신 직접 실행(조각 2개·직렬, fg-run "규모가 작으면 직접").
- 스모크 DoD 3: 1/6 테스트에 단계를 끼우지 않고 독립 테스트로 더함(서로 영향 없게).
- UAT: 루프 계약대로 실제 claude로 에이전트가 확인한다. 모델은 비용을 줄이려 계획 역할을 `haiku`로 설정한 임시 데이터 폴더에서 돌리고, 프로젝트는 이미 신뢰된 이 워크트리 폴더를 쓴다(새 폴더는 claude가 신뢰 확인을 물어 대화 ID가 안 생긴다). 실제 재부팅은 루프 밖이다.
- UAT 판정: 에이전트가 실제 claude(haiku)로 대화 → 서버 SIGKILL → 재기동 후 같은 대화 ID 복구와 이전 대화 재표시를 확인해 `verified: yes`로 기록(증거 `.forge/verify/electron-app-2of6/261031-011305`). 작업 도중(작업 중 상태)에 끊긴 경우는 확인하지 않았다.
