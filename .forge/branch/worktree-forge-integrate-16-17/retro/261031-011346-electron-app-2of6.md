# 2026-10-31 — 데스크톱 앱 2/6: 서버가 어떻게 내려가든 세션을 `claude --resume`으로 대화째 복구

## 계획 대비 실제
- 계획대로 된 것:
  - S1(복구 목록 `restore.json`)과 S2(서버 시작 때 복구)를 테스트 먼저 쓰는 순서로 넣었다. SIGTERM·SIGKILL 두 신호에서 모두 목록이 남는 것을 테스트로 고정했다.
  - 에이전트 UAT에서 실제 claude가 같은 대화 ID(`bda82f5e…`)로 다시 떴고, 이전 대화가 화면에 다시 그려졌다.
- 어긋난 것:
  - **그릴링 때 따로 쓴 독립 검사(`restore-probe.mjs`)가 실행 단계 테스트가 못 본 틈을 잡았다.** 훅이 대화 ID를 알린 뒤 복구 목록에 옮겨지기까지 파일 감시 지연이 150ms 있다. 그 사이 서버가 죽으면 `--resume` 없이 새 대화로 떴다. 실행 단계 테스트는 "목록에 ID가 들어갈 때까지 기다린 뒤" 서버를 꺼서 이 틈을 지나쳤다. 복구할 때 훅이 직접 쓴 상태 파일의 ID를 먼저 보게 고쳤다.
  - 계획에 없던 모듈 단계 `ready`(포트를 잡은 뒤)를 만들었다. 포트를 못 잡은 두 번째 서버가 claude를 띄우지 않게 하려는 것이다.
  - 대화 ID 모양 검사를 더했다. 상태 파일 값을 claude 인자로 넘기기 때문이다.

## 배운 점
- 다음엔 다르게:
  - **무인 루프의 멈춤 조건에는 실행 단계와 따로 쓴 독립 검사를 둔다.** 같은 손이 쓴 테스트는 구현의 가정(이번에는 "목록이 먼저 반영된다")을 그대로 물려받는다. 그릴링 때 실제 진입점·API만으로 동작을 재는 스크립트를 쓰고, 가짜 claude 같은 도구도 사본으로 떼어 두면 이런 틈을 잡는다.
  - **"상태가 두 곳에 있으면 어느 쪽이 먼저 쓰이는지"를 테스트 시나리오에 넣는다.** 훅이 쓰는 상태 파일과 서버가 옮겨 적는 목록처럼 반영 지연이 있는 쌍은, 그 지연 안에서 죽는 경우를 따로 본다.
  - 실제 claude로 하는 UAT는 이미 신뢰된 폴더를 쓴다. 새 폴더는 claude가 신뢰 확인을 물어 SessionStart 훅이 늦어지고, 그러면 대화 ID가 생기지 않는다.
