# 2026-10-27 — 준비물 확인 중에는 '확인 중…'을 보이고 옛 결과를 숨긴다 (v0.1.7)

## 계획 대비 실제
- 계획대로 된 것: S0(붙잡아 둘 수 있는 가짜 `deps_status` + e2e 3건, 수정 전 빨강) → S1(`depsSeq` 순번 + `depsChecking`) → S2(0.1.7). DoD 4개 모두 기준선 → 목표값으로 확인.
- 어긋난 것:
  - **순서 보호 검사 (다)의 두 번째 확인 경로**: 확인 중에는 두 버튼이 꺼지므로(결정 2) 버튼으로는 확인을 겹칠 수 없었다. 설정 > 언어 변경(`.then(checkDeps)`)으로 두 번째 확인을 띄웠고, 설정 패널이 그려지도록 가짜 IPC에 `model_settings: {}`를 더했다.
  - **계획 파일 위치**: fg-ask가 워크트리(기본 브랜치가 아님)의 최상위 `.forge/backlog/`(gitignore)에 계획을 쓰고 메인 체크아웃으로 복사했다. 이 브랜치의 forge 루트(`.forge/branch/<branch>/`)는 비어 있어, 상태 머신대로라면 "할 일 없음 → fg-ask"로 읽힐 뻔했다. 계획의 '브랜치·머지' 절을 근거로 브랜치 루트 `plan.md`로 옮겨 실행했다.

## 배운 점
- 다음엔 다르게:
  - **진행 중에 버튼을 끄는 화면에서 응답 순서를 검사할 때는, 버튼이 아닌 두 번째 호출 경로를 계획 단계에서 미리 적는다**(여기서는 언어 변경). 없으면 순서 보호 코드가 실제로는 도달 불가능한 경로만 지키는 것일 수 있다.
  - **같은 브랜치에서 이어 실행할 계획**(후속후보 원장 변경과 합쳐 머지하는 경우)은 fg-ask 때 메인 체크아웃 복사와 함께 브랜치 루트 `backlog/`에도 둔다. 그래야 fg-next/fg-status가 이 워크트리에서 바로 fg-run으로 읽는다.
  - `check-release.sh`는 HEAD 복제본으로 검사하므로 버전 변경은 커밋한 뒤 돌린다(task 9 때와 같은 함정 — 이번엔 미리 알고 피했다).
